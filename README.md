# Signia Solutions — website

A rebuild of [signiasolutions.com](https://signiasolutions.com/): same brand, same voice,
same content — rewritten as a fast, accessible, search-engine-visible static site.

- **Stack:** hand-written HTML5, one CSS file, one JS file. No framework, no build
  dependencies, no third-party requests at runtime.
- **Critical path:** ~69 KB uncompressed (HTML + CSS + JS) for the homepage, against
  33 scripts and 25 stylesheets on the current WordPress build.
- **Deploys to:** Netlify, Cloudflare Pages, Vercel, GitHub Pages, S3+CloudFront, or
  straight into an Apache/cPanel `public_html`.

---

## 1. Why this rebuild was needed — the audit

Every finding below was verified against the live site's HTML on 2026-08-25, not assumed.

| # | Finding | Evidence | Severity |
|---|---|---|---|
| 1 | **The entire site tells Google not to index it.** | `<meta name='robots' content='noindex, nofollow' />` on every page | 🔴 Critical |
| 2 | No meta description anywhere | 0 `<meta name="description">` tags | 🔴 High |
| 3 | No Open Graph or Twitter Card tags | 0 `og:*`, 0 `twitter:*` | 🔴 High |
| 4 | No structured data | 0 `application/ld+json` blocks | 🔴 High |
| 5 | Title is off-target: *"Signia Solutions – Staffing Simplified"* | doesn't contain *nurse triage*, *after hours*, *senior living*, or a location | 🔴 High |
| 6 | Pinch-zoom disabled | `user-scalable=no, maximum-scale=1` — fails WCAG 1.4.4 | 🟠 Medium |
| 7 | Page-builder weight | 33 `<script>`, 25 stylesheets, 90 KB of HTML for one screen of copy | 🟠 Medium |
| 8 | Content images have empty `alt` | `alt=""` on the nurse photo and the award badge | 🟠 Medium |
| 9 | Almost no heading structure | 1 `<h1>`, 1 `<h2>`, 0 `<h3>` on the whole homepage — the Tatsu builder renders headings as `<div>`s | 🟠 Medium |
| 10 | No sitemap referenced, no `robots.txt` directive | — | 🟡 Low |

**Finding #1 is the one that matters.** No amount of content or keyword work does anything
while `noindex, nofollow` is on the page. It has to come off before anything else counts.

There is a silver lining: because nothing is indexed, there is **no ranking equity to
protect**, so this rebuild was free to fix the URL slugs (`/who/` → `/who-we-are/`,
`/triage/` → `/nurse-triage/`) instead of inheriting them. Redirects are still shipped for
bookmarks, email signatures and directory listings.

## 2. What ships

```
.
├── index.html                  Home
├── nurse-triage/               Service page — the primary ranking target
├── who-we-are/                 About
├── careers/                    Careers + application form
├── contact/                    Contact + inquiry form
├── privacy/                    Privacy policy (needs legal review — see §7)
├── accessibility/              Accessibility statement
├── 404.html                    Styled, noindex, links back into the site
├── robots.txt                  Explicitly allows crawling; points at the sitemap
├── sitemap.xml                 Generated by the build
├── site.webmanifest            Installable-app metadata
├── _redirects / _headers       Netlify + Cloudflare Pages config
├── .htaccess                   Apache equivalent (redirects, headers, gzip, caching)
├── assets/
│   ├── css/site.css            The entire stylesheet
│   ├── js/site.js              ~6 KB, all progressive enhancement
│   └── img/                    Logo, favicons, OG image, optimised photos
└── tools/                      Build inputs — NOT web content
    ├── build.py                Composes pages from partials
    ├── partials/               Header, footer, icon sprite
    └── pages/                  Per-page body content
```

### Editing content

**Never hand-edit the generated `.html` files in the site root.** They are overwritten.

1. Body copy → `tools/pages/<page>.html`
2. Nav, footer, icons → `tools/partials/`
3. Titles, meta descriptions, schema, sitemap entries → `PAGES_MANIFEST` in `tools/build.py`
4. FAQ content → `FAQ_ITEMS` in `tools/build.py` (feeds the visible FAQ **and** the
   `FAQPage` schema from one source, so the two can never drift)

Then:

```bash
python tools/build.py
```

Standard library only — any Python 3.9+ will do. Output is plain static HTML.

## 3. Brand

Everything is derived from the real logo, not eyeballed.

| Token | Value | Where it's used |
|---|---|---|
| `--brand` | `#0094EF` | The exact colour of the official logo file. Marks, icons, borders, focus ring, large display numerals. |
| `--brand-action` | `#0076BF` | Button fills. **Not** the logo blue — white text on `#0094EF` is only 3.24:1 and fails WCAG AA. |
| `--brand-ink` | `#0069AE` | Body-size links and eyebrow labels (5.78:1 on white). |
| `--ink` | `#18212F` | Headlines and dark sections — taken from the live site's own CSS. |
| `--brand-tint` | `#EAF4FE` | Section washes, icon chips. |

`assets/img/signia-mark.svg` is a **pixel-exact vector trace** of the logo mark from
`Signia.png` — verified as 0 mismatched pixels against the original raster. It inherits
`currentColor`, so it recolours cleanly on dark backgrounds and scales to any size.
The original PNG is kept at `assets/img/signia-logo-original.png` for reference.

That inheritance was claimed here before it was true. The `#signia-mark` sprite symbol
carried no `fill`, so every `<rect>` in it fell back to the SVG default of black and the
mark rendered `rgb(0,0,0)` in the header and footer regardless of the `color: var(--brand)`
sitting on `.brand__mark`. Fixed 2026-09-03 by putting `fill="currentColor"` on the
symbol's group; the mark now renders in the logo blue it was always supposed to be.

Type is a system font stack: zero network requests, zero layout shift, native rendering
on every platform. If a licensed brand typeface is ever adopted, self-host it and add
`font-display: swap` — do not link Google Fonts, it re-introduces a third-party
dependency and a render-blocking round trip.

## 4. SEO implementation

**Per page**
- Unique `<title>` (all ≤ 58 characters — no SERP truncation) and `<meta description>` (≤ 160)
- Self-referencing `<link rel="canonical">`
- `index, follow, max-image-preview:large, max-snippet:-1` — the opposite of what the old site sent
- Full Open Graph + Twitter Card set with a purpose-built 1200×630 share image
- Exactly one `<h1>`, with a heading outline that never skips a level (verified in build checks)

**Structured data** — one `@graph` block per page, all cross-linked by `@id`:

| Type | Where | Why |
|---|---|---|
| `Organization` | every page | Knowledge-panel and brand-entity signal |
| `MedicalBusiness` + `LocalBusiness` | every page | Local pack eligibility for Plymouth / Twin Cities |
| `WebSite` | every page | Site-level entity |
| `WebPage` / `AboutPage` / `ContactPage` | per page | Page typing |
| `BreadcrumbList` | per page | Breadcrumb rich result |
| `Service` + `OfferCatalog` | home, nurse-triage | Describes what is actually sold |
| `FAQPage` | **nurse-triage only** | Duplicating one FAQ set across pages competes with itself |

**Keyword targeting** — mapped to what buyers (owners, administrators, DONs) actually search:

| Page | Primary | Supporting |
|---|---|---|
| Home | after-hours RN triage for senior living | after hours nurse senior living, on-call RN assisted living |
| Nurse Triage | after-hours nurse triage assisted living / memory care | reduce unnecessary ER transfers assisted living, outsourced on-call nursing, senior living triage workflow |
| Who We Are | Minnesota nurse triage company | RN triage senior living Minnesota |
| Careers | remote RN triage jobs Minnesota | triage nurse jobs senior living |
| Contact | nurse triage Plymouth MN | after hours nursing Twin Cities |

**Answer-engine (AEO) readiness.** The eight FAQ answers are written to stand alone
without page context, so ChatGPT / Perplexity / AI Overviews can quote one whole and have
it make sense. That is also why the service description repeats the plain-language
definition of after-hours nurse triage rather than assuming the reader knows it.

**Local SEO.** NAP (name, address, phone) is identical in the footer, on the contact page
and inside `LocalBusiness` schema on every page. Keep it byte-identical everywhere,
including the Google Business Profile — inconsistent NAP is the most common cause of a
business failing to surface in the local pack.

**Performance** = the Core Web Vitals half of SEO: no render-blocking third parties, a
single deferred script, WebP images with explicit `width`/`height` (so CLS is structurally
zero), `loading="lazy"` below the fold, and a system font stack (no FOIT/FOUT).

## 5. Accessibility

Built to WCAG 2.2 AA and verified, not assumed:

- Every text/background pair in the palette was measured. The only two that failed
  (white on the logo blue, and the form-field border) were fixed by introducing
  `--brand-action` and `--line-ui` rather than by lowering the bar.
- Skip link, semantic landmarks, one `h1` per page, no skipped heading levels.
- Full keyboard operation; the mobile menu closes on `Escape` and returns focus.
- Visible focus indicators everywhere (`:focus-visible`, 2px, 3px offset).
- Pinch-zoom **enabled** — the old `maximum-scale=1` is gone.
- All animation is gated behind `prefers-reduced-motion`.
- Every form control has a real `<label for>`; icons are `aria-hidden`; informative
  images carry meaningful `alt`.
- Layout reflows cleanly to 320 px with no horizontal scroll.

## 6. Wiring up the forms

A static site has no server, so the two forms need an endpoint. Both are marked
`action="REPLACE_ME_WITH_YOUR_FORM_ENDPOINT"` and will refuse to submit until that is
changed — deliberately, so a broken form can't silently swallow a lead.

**Option A — Netlify / Cloudflare Pages Forms (simplest).** The `data-netlify="true"`
and hidden `form-name` fields are already in place. Delete the `data-ajax="true"`
attribute and set `action="/contact/"`, then enable Forms in the dashboard.

**Option B — a hosted form endpoint** (Formspree, Basin, Getform, a Zapier catch hook, or
your own handler). Paste the endpoint URL into `action` and leave `data-ajax="true"` —
`site.js` posts in the background and shows an inline confirmation without a page reload.

Both forms already include a honeypot field, client-side validation, and a disabled
submit button while a request is in flight.

> **Compliance note.** These forms are for business inquiries and job applications only.
> Whatever endpoint you choose is a third party and is almost certainly **not** covered by
> a business associate agreement. Never route protected health information through them.
> Both forms say so on the page; keep that copy.

## 7. Before launch — checklist

- [ ] **Replace the form endpoints** (§6). Submit a test message and confirm it arrives.
- [ ] **Have counsel review `privacy/`.** It is an accurate draft of how the site behaves,
      but it is not legal advice. Remove the yellow review notice once approved.
- [ ] **Confirm the LeadingAge Minnesota partnership.** The badge inherited from the old
      site was captioned "Best Places to Work Minnesota, 2026"; it is in fact the
      LeadingAge Minnesota *Business Partner* mark — a partner designation, not an award.
      The award claim is gone and the mark now sits in the footer worded as a partnership.
      Verify the partnership is current for 2026 and that LeadingAge's mark-usage terms
      allow display; if not, drop `.footer__partner` from `tools/partials/footer.html`.
- [ ] **Pick a canonical host** (www or non-www) and make the other 301 to it. Both
      `.htaccess` and `_redirects` assume **non-www**; flip them if you prefer www.
- [ ] **Verify the redirects fire**: `/who/` → `/who-we-are/` and `/triage/` → `/nurse-triage/`,
      both returning `301`.
- [ ] **Verify `robots.txt` and every page's robots meta say `index`.** This is the fix for
      audit finding #1 — check it in production, not just locally.
- [ ] **Google Search Console**: add the property, submit `https://signiasolutions.com/sitemap.xml`,
      then use *URL Inspection → Request Indexing* on the homepage and `/nurse-triage/`.
      Because the site has been `noindex` up to now, Google has nothing cached — the first
      crawl is effectively a new site launch.
- [ ] **Bing Webmaster Tools**: same, and it feeds ChatGPT search results.
- [ ] **Google Business Profile**: claim/update it, and make the NAP match the footer exactly.
- [ ] **Validate the structured data** at [validator.schema.org](https://validator.schema.org/)
      and Google's [Rich Results Test](https://search.google.com/test/rich-results).
- [ ] **Run Lighthouse** on the deployed URL (mobile profile) and keep a screenshot as a baseline.
- [ ] **Decide on analytics.** Nothing is installed. If you add Google Analytics, add a
      cookie notice and update `privacy/`; if you would rather not, Plausible or Fathom are
      cookie-free and need no banner. Either way, add the domain to the `_headers` /
      `.htaccess` CSP — the current policy is `default-src 'self'` and will block it.

## 8. Deploying

### Azure Static Web Apps — **currently live here**

| | |
|---|---|
| **URL** | https://polite-water-07a742710.7.azurestaticapps.net |
| Resource group | `signia-triage-rg` (centralus) |
| App name | `signia-triage` |
| SKU | Free |

Azure ignores `_redirects` and `.htaccess`, so all routing, headers and 404
handling for this host live in **`staticwebapp.config.json`**. Edit that file if
you change either of the other two.

Deploy from the repo root:

```bash
python tools/build.py
TOKEN=$(az staticwebapp secrets list --name signia-triage \
          --resource-group signia-triage-rg --query "properties.apiKey" -o tsv)
npx @azure/static-web-apps-cli deploy . --env production --deployment-token "$TOKEN"
```

**Two Azure-specific traps, both hit during setup and both now documented in the
config file itself:**

1. `trailingSlash: "always"` appends a slash to *every* path, files included — so
   `/robots.txt` 301s to `/robots.txt/` and every CSS/JS/image request costs an
   extra round trip. Leave `trailingSlash` unset.
2. `navigationFallback` is an SPA feature: it rewrites unmatched routes and
   returns **HTTP 200**, turning every bad URL into a soft 404. Use
   `responseOverrides` instead so a missing page returns a real 404.

Also note Azure normalises `/who` and `/who/` to the same rule, so declaring both
fails the deployment outright. Declare the trailing-slash form only; it matches both.

To wire up push-to-deploy, add the deployment token to the repo as a secret named
`AZURE_STATIC_WEB_APPS_API_TOKEN` and add a workflow using
`Azure/static-web-apps-deploy@v1`.

### Netlify / Cloudflare Pages
Connect the repository. Build command: *(none)*. Publish directory: `/`.
`_redirects` and `_headers` are picked up automatically.

### Apache / cPanel (replacing the WordPress install)
Upload everything except `tools/` into `public_html`. `.htaccess` handles HTTPS, the
canonical host, legacy-slug redirects, security headers, gzip and caching. Take a full
backup of the WordPress site and database first.

### Any other host
Serve the directory as static files, and replicate three things: the 301s from `_redirects`,
the security headers from `_headers`, and `404.html` as the error document.

### Local preview
```bash
python -m http.server 8000
# http://localhost:8000
```

## 9. Where to take it next

Ranked by likely return, now that the site can actually be indexed:

1. **Case studies / outcomes.** The single biggest gap. Buyers want *"this community cut
   transfers by X"*. Add real numbers as soon as you can substantiate them — and only then.
   Nothing on this site currently claims a statistic, deliberately.
2. **A resources section.** Two or three genuinely useful articles — *when to outsource
   after-hours on-call nursing*, *what to look for in a triage partner*, *how triage
   documentation supports a state survey* — would target the top-of-funnel searches the
   service pages can't reach.
3. **Location pages**, if you serve beyond the Twin Cities metro. One page per market, with
   real local content — not the same page with the city name swapped.
4. **Named clinical leadership** on Who We Are, with photos and credentials, plus `Person`
   schema. For a health service, E-E-A-T is a ranking factor and named RNs carry it.
5. **Testimonials** with `Review` schema, once you have permission to publish them.
6. **Real `JobPosting` schema** on Careers when specific roles open — it makes listings
   eligible for the Google Jobs box. It is deliberately absent now, because posting
   `JobPosting` markup with no actual open role is a structured-data violation.
